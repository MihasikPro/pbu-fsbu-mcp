# Как дополнять pbu-fsbu-mcp

## Проекция на 1С

Файлы: `data/sources/mappings/bp30/<standard-id>.yaml`.

1. Убедитесь, что объект есть в `data/sources/objects/bp30.yaml`. Если нет — добавьте, сверив имя с реальной конфигурацией, а не по памяти.
2. Одна запись — одна связь «пункт → объект». Пункт, реализованный тремя объектами, даёт три записи.
3. `note` объясняет, **как именно** объект реализует норму. Пересказ самой нормы в `note` не нужен: её текст уже отдаёт `get_clause`.
4. `confidence` — целое 0–100. **Ниже 60 не коммитим.** Сомнительная привязка хуже отсутствующей: она выглядит достоверной. Завышение числа ради прохождения этого порога — как раз то, от чего порог защищает.
5. `verified` по умолчанию `false`. В `true` его переводит только человек, вручную сверивший запись с текстом пункта и с конфигурацией — сама запись этого сделать не может.
6. Пересоберите корпус и прогоните тесты:

   ```bash
   uv run python -m etl.build_db && uv run python -m etl.validate && uv run pytest
   ```

## Ссылки на ИТС

Файлы: `data/sources/its/<standard-id>.yaml`.

1. `its_id` находится инструментом `its_help` сервера `1c-code-check-mcp` и **проверяется** вызовом `fetch_its`. Неразрешимый идентификатор коммитить нельзя.
2. `summary` — **своими словами**, не более 400 символов. Копирование текста ИТС запрещено: это лицензионный контент 1С. Полные тексты статей в репозиторий не попадают ни при каких обстоятельствах.
3. `verified` по умолчанию `false`, как и у проекции на 1С; в `true` его переводит только человек.

## Нормативные тексты

Файлы: `data/sources/standards/<standard-id>.yaml`. Тексты пунктов переносятся дословно из официального приказа Минфина. Сокращать, пересказывать и «причёсывать» формулировки нельзя. Процедура обновления описана в README, раздел «Обновление корпуса».

### Вычитка OCR

Официальные источники (Минфин, publication.pravo.gov.ru) публикуют приказы об
утверждении ФСБУ сканами без текстового слоя. Текст пунктов получается через
`etl.ocr_text.extract` (Tesseract 5.x, модель `rus` из `tessdata_best`) и затем
обязан быть выверен человеком построчно по оригиналу скана — OCR-текст не
попадает в корпус без вычитки.

При вычитке каждого стандарта, распознанного из приказа 204н, целенаправленно
проверяйте следующие классы ошибок, уже встречавшиеся на практике:

| Класс ошибки | Пример искажения | Как проверять |
|---|---|---|
| Буква подпункта распознаётся как цифра | `б)` → `6)` | Сверять маркеры подпунктов визуально со сканом, не доверять цифрам в начале строки внутри перечней |
| Ноль в дате распознаётся как `@` | `17.09.2020` → `17.09.202@` | Сверять все даты в тексте посимвольно со сканом |
| Вставленные тире на месте выключки (обоснованного выравнивания) | лишний `-` в месте пробела при выравнивании по ширине | Проверять места, где в оригинале текст выключен по ширине страницы |
| Разрывы слов на границе страниц | слово, начатое на одной странице скана и продолженное на следующей, может остаться разорванным или дать лишний перенос после `normalise_hyphenation` | Проверять последнюю и первую строки соседних страниц на стыке |

Эти классы ошибок не исчерпывающие — при обнаружении нового устойчивого искажения
добавьте строку в таблицу.
